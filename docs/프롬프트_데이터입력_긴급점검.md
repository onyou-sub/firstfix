# FixFirst — 데이터 입력 → 경고 → 긴급 점검 구현 프롬프트

> 목표: 관리자가 임의로 센서·에러 데이터를 올리면, 시스템이 바로 고장 위험을 판단해 경고를 띄우고,
> 가장 빨리 비는 팀에 긴급 점검을 바로 배정한다. 관리자 승인은 없다.
> 작업자는 알림을 보고 바로 [출동 확인]을 누르고, 관리자는 "어느 팀에 넘어갔고 지금 어디까지 왔는지"만 본다.
>
> 진행 방식: 0번 공통 컨텍스트를 매 요청 맨 앞에 붙이고, 1 → 2 → 3 → 4단계를 한 번에 하나씩 요청한다.
> 각 단계의 완료 기준을 직접 확인한 뒤 git commit 하고 다음 단계로 넘어간다.

## 0. 공통 컨텍스트 (매 요청 맨 앞에 붙이기)

````text
[프로젝트] fixfirst — 설비 고장 예측·정비 우선순위 에이전트 (Supervisor 멀티 에이전트, Streamlit)

[현재 구조]
- 원본 데이터: data/pdm.db (telemetry, errors, maint, failures, machines, parts_stock, criticality, work_standards, teams)
  datetime은 'YYYY-MM-DD HH:MM:SS' 문자열. 원본은 절대 수정하지 않는다.
- 운영 DB: data/app.db (store/app_db.py) — work_orders, purchase_orders, notifications, work_reports, maint_log,
  stock_ledger, sessions, app_state. 알림은 app_db.notify(title=, body=, to_role=, to_team=, as_of_date=, ...)
- 예측: ml/features.py build_features(as_of) → ml/predict.py predict_df(as_of)
  (machine_id, top_comp, top_prob, high_risk). 학습용 build_training_table은 원본만 쓴다.
- 조사 도구: tools/data_tools.py 의 _sensor_rows(machine_id, sensor, hours, as_of), _error_rows(machine_id, days, as_of)
  — 모든 조회는 datetime <= as_of. _maint_rows는 이미 원본 + app.db maint_log를 합쳐 읽는다 (같은 방식 참고).
- 조사: agents/investigator.py investigate_one(machine_id, comp, prob, as_of) -> (Finding, evidence_id)
- 일정: tools/plan_tools.py build_tasks(...), schedule_tasks(rows, teams_info, available_teams, team_available),
  load_teams(), 운영 설정 ops_settings.load_settings()
- 화면 연결층: services.py (화면은 services만 호출), 화면: views/*.py, 공통 부품: ui/components.py
- 부품-센서 짝: motor=volt(상승), drive=rotate(하락), pump=pressure(상승), bearing=vibration(상승)
  관련 에러: motor=overvoltage, drive=low_rpm·torque, pump=pressure, bearing=vibration
  센서 1년 평균: volt 170.8, rotate 446.6, pressure 100.9, vibration 40.4 (tools/data_tools.py SENSOR_MEAN)
- 환경: Python 3.13, uv, langchain 1.4, langgraph 1.2, streamlit, gpt-5.4-mini

[반드시 지킬 규칙]
1. 원본 pdm.db는 수정하지 않는다. 입력 데이터는 app.db에만 저장한다.
2. 기준 시각 규칙 유지: 입력 데이터도 datetime <= as_of 인 것만 예측·조사에 보인다.
3. 판단·계산은 코드, LLM은 조사 에이전트(기존)만 쓴다. 새 LLM 호출을 만들지 않는다.
4. 긴급 "점검" 작업은 관리자 승인 없이 항상 자동 배정한다 (켜기/끄기 설정 없음).
   관리자에게는 배정 결과(설비, 부품, 배정 팀, 출동 시각)만 알린다.
   부품 교체 작업 지시와 발주는 기존처럼 관리자 승인(HITL) 후에만 등록한다. 설비 정지·제어 기능은 만들지 않는다.
5. 도구·함수는 예외 대신 오류 문자열을 돌려주는 기존 방식을 따른다. 요청하지 않은 파일은 건드리지 않는다.
6. 각 단계 끝에 실행 방법과 테스트 명령을 알려준다.
````

## 2단계. 즉시 판단과 경고

````text
[0. 공통 컨텍스트]

2단계: 1단계로 입력 데이터가 예측에 반영된다. 데이터가 들어오는 즉시 해당 설비를 판단해 경고를 만든다. LLM은 쓰지 않는다.

[만들 것]
1. app.db 테이블 alerts
   (alert_id TEXT PK, as_of TEXT, machine_id INTEGER, comp TEXT, prob REAL, level TEXT, source TEXT,
    batch_id TEXT, status TEXT, evidence_id TEXT, wo_id TEXT, message TEXT, created_at TEXT, updated_at TEXT)
   - level: 경고 / 주의 / 사람 확인 / 정상
   - source: 모델 / 규칙
   - status: 열림 → 점검 배정 → 출동 → 점검 완료 / 종료 (정상이면 저장하지 않음)
   - investigating INTEGER DEFAULT 0 (조사 에이전트가 도는 동안 1, 배정과 별개로 표시)

2. services.evaluate_machine(machine_id, as_of, batch_id=None) -> dict
   - predict_df(as_of)에서 해당 설비의 top_comp, top_prob, high_risk (LLM 없음)
   - 판정 순서
     ① 예측 부품을 최근 7일 안에 교체(_maint_rows 기준) → "사람 확인"
     ② high_risk → "경고"(모델)
     ③ 짝 센서 최근 3시간 평균이 1년 평균 대비 +30% 이상(rotate는 -20% 이하) → "경고"(규칙),
        이때 comp는 그 센서의 짝 부품, prob는 모델 값 그대로 기록
     ④ top_prob >= 0.3 → "주의"
     ⑤ 그 외 "정상"
   - 같은 설비에 status가 종료/점검 완료가 아닌 경고가 이미 있으면 새로 만들지 않고 그 경고를 반환 (중복 방지)
   - 이 단계에서는 관리자 알림을 보내지 않는다. 관리자 알림은 3단계에서 배정이 끝난 뒤 한 번만 보낸다.
   - 반환: {"alert_id", "machine_id", "comp", "prob", "level", "source", "is_new"}

3. 1단계 입력 함수(add_scenario, add_manual, add_csv)가 저장 직후 입력된 설비마다 evaluate_machine을 호출하고,
   결과 목록을 반환값 "alerts"에 포함

4. 조회 함수: services.open_alerts(as_of) (열린 경고, 최신순), services.alert_history(limit=50)

5. 테스트 scripts/test_live_eval.py (LLM 없음)
   - #45 bearing_vibration 시나리오 → level "경고", status "열림"
   - 같은 시나리오 한 번 더 → 경고 1건 유지 (is_new False)
   - 정상 범위 manual 입력(진동 41) → 경고 없음
   - 모델은 낮지만 manual로 진동 60을 6시간 → "경고"(규칙)
   - 최근 7일 안에 교체한 설비에 시나리오 → "사람 확인"
- 실행: uv run python scripts/test_live_eval.py
````

**완료 기준**
- [ ] 시나리오 입력 직후 경고가 생김
- [ ] 같은 입력을 반복해도 경고가 늘지 않음
- [ ] 모델이 못 잡는 큰 변화는 규칙 경고로 잡힘

> 시나리오를 넣었는데 "경고"가 안 나오면, 모델이 반응할 만큼 변화가 길지 않은 경우입니다.
> 테스트 출력에 그 설비의 top_prob를 함께 찍게 해서 hours(18 → 24)나 상승 폭을 조정하세요.

## 3단계. 자동 조사와 긴급 점검 배정

````text
[0. 공통 컨텍스트]

3단계: 2단계로 경고가 생긴다. 경고가 생기면 그 설비를 바로 조사하고, 가장 빨리 비는 팀을 긴급 점검에 보낸다.

[만들 것]
1. services.handle_alert(alert_id) — 새 경고(is_new)일 때 백그라운드 스레드로 실행, 화면을 막지 않는다
   ① status "조사 중" → investigate_one(machine_id, comp, prob, as_of) (입력 데이터 포함, 기존 조사 에이전트 그대로)
      조사 실패 시 status "종료", message에 오류, 관리자 알림
   ② 결과 label에 따라 작업 종류 결정
      - "예측 고장" → 긴급 점검(urgent_check, 60분)
      - "센서·설치 이상 가능성" → 센서 점검(sensor_check, 60분)
   ③ 배치: 가장 빨리 비는 팀
      - tools/plan_tools.py schedule_tasks에 선택 인자 start_from: str | None 추가
        (주어지면 모든 팀의 시작 가능 시각을 max(근무 시작, start_from)으로)
      - start_from = as_of의 시각(예: 06:00이면 근무 시작 09:00, 14:20이면 14:20)
      - 오늘 이미 있는 작업(app.db work_orders, 같은 as_of_date)은 팀별로 고정 점유 시간으로 반영해 겹치지 않게
      - 전문 팀 우선 규칙은 기존과 같음. 오늘 근무 시간 안에 못 끝나면 "내일 첫 작업"으로 표시하고 관리자 알림
      - 기존 아침 배정안(outputs/plans)은 바꾸지 않는다. 긴급 작업은 work_orders에만 추가한다.
   ④ 자동 배정 (운영 설정 auto_dispatch_urgent=True일 때)
      - app.db work_orders에 바로 생성: wo_id "UWO-{MMDD}-{machine_id:03d}-{순번}", status ASSIGNED, urgent=1,
        task_type urgent_check/sensor_check, team, start, end, evidence_id, title, checklist(조사 결과 steps의 action),
        approved_by="auto(긴급 점검)"
        (work_orders에 urgent 컬럼이 없으면 ALTER TABLE로 추가, 기존 행은 0)
      - 해당 팀 작업자 알림: "긴급 점검: #45 베어링 — 14:20 출동 (근거 E1112-045)"
      - 관리자 알림: "#45 긴급 점검을 2팀에 자동 배정했습니다"
      - status "점검 배정", alerts.wo_id 기록
   ⑤ auto_dispatch_urgent=False면 자동 등록 대신 관리자 승인 카드용 초안(UWO, PENDING)을 만들고 관리자 알림만
   ⑥ 부품 교체가 필요해 보여도 교체 작업 지시·발주는 만들지 않는다.
      (작업자가 점검 완료 보고에서 "교체 필요"를 남기면 관리자가 기존 흐름으로 처리)
   ⑦ 작업자가 긴급 작업을 완료 보고하면(services.complete_work 기존 흐름) alerts.status "점검 완료"

2. 운영 설정 (ops_settings.py DEFAULTS, 설정 페이지)
   - auto_dispatch_urgent: True (긴급 점검 자동 배정)
   - urgent_check_min: 60
   - 검증 규칙 추가

3. 동시성
   - 같은 경고에 handle_alert가 두 번 실행되지 않게 alert_id 단위 잠금
   - 시간당 자동 조사 최대 10건 (초과 시 status "대기", 다음 입력 때 처리)

4. 테스트 scripts/test_live_alert.py (조사 에이전트 LLM 사용)
   - 2015-11-12 06:00:00, #45 bearing_vibration 시나리오
     → 경고 → evidence/20151112/45.json 생성 → UWO 작업 지시 ASSIGNED(urgent=1) → 해당 팀 알림 1건
     → 교체 작업 지시·발주 초안은 생기지 않음
   - 같은 날 그 팀에 기존 작업이 있으면 긴급 작업 시간이 겹치지 않음
   - auto_dispatch_urgent=False → PENDING 초안만 생기고 작업자 알림 없음
   - 작업자로 complete_work 실행 → alerts.status "점검 완료", 장기 기억·현장 메모에 반영
- 실행: uv run python scripts/test_live_alert.py
````

**완료 기준**
- [ ] 데이터를 넣으면 사람이 아무것도 누르지 않아도 조사 → 긴급 점검 배정 → 작업자 알림까지 진행됨
- [ ] 교체·발주는 자동으로 등록되지 않음
- [ ] 긴급 작업이 기존 작업과 시간이 겹치지 않음

````text

4단계: 1~3단계 기능을 화면에 연결한다. 이모지 금지, 제목 옆 영어 병기 금지, 상태는 텍스트 배지 (기존 화면 규칙 유지).
````

## 시연 순서

1. 브라우저 두 개: 왼쪽 관리자, 오른쪽 2팀 작업자로 로그인. 기준 시각 2015-11-12
2. 관리자 › 데이터 입력 › 설비 #45 › [베어링 진동 상승] (미리보기 차트로 진동이 오르는 것 확인)
3. 몇 초 뒤 상단 빨간 배너 "경고: #45 베어링 고장 위험 …"
4. 경고 상태가 조사 중 → 점검 배정(2팀 시각)으로 바뀜, 대시보드 간트에 긴급 작업 표시
5. 오른쪽 작업자 화면에 "긴급 점검: #45 — 출동" 알림, 작업 카드 맨 위
6. 작업자 완료 보고 → 관리자에게 완료 알림, 경고 상태 "점검 완료"
7. 관리자 › 데이터 입력 › 입력 데이터 지우기 → 원래 상태로 복귀
